## 一、需求整理（浓缩）

### 1.1 产品与五端

多租户餐饮 SaaS，五端协同。**注意：现有前端四端均为 2019–2020 年老栈，目标态是重写三端 + Taro 点餐（见 3.2）**。

| 端 | 角色 | 后端 | 现状 / 目标 |
|---|---|---|---|
| 运营中心 | 平台运营 | operator_web（BFF） | 目标 Vue3 重写 |
| 管家端（企业） | 企业账号、门店经理 | enterprise_web（BFF） | 目标 Vue3 重写 |
| 收银端 | 门店收银员 | cash_web（BFF） | 目标 Vue3 重写（触屏大按钮） |
| 点餐 H5 / 小程序 | 顾客 C 端 | **microapp_web（新增 8087 `/microApp`）** | 目标 Taro 4 双端 |
| 收银 APP（Flutter） | 门店收银员 | 既有原生应用 | **本轮不动**（老栈风险见 3.2） |

### 1.2 角色与登录入口

四套 B 端登录均在 provider 契约层，当前签发 JWT（过渡），阶段 5 统一 Sa-Token：

| 角色 | 端点 | 参数 |
|---|---|---|
| 运营人员 | `POST /operator/user/login` | loginName / loginPass |
| 企业账号 | `POST /enterprise/account/login` | shopId / phone / loginPass |
| 门店经理 | `POST /store/manager/login` | shopId / phone / loginPass |
| 门店员工 | `POST /staff/login` | shopId / **loginName（姓名）** / **password（命名与上面三套不一致，K13）** |

多租户：`shop_id`（集团）+ `store_id`（门店）；HTTP 头 `X-Tenant-Shop-Id / X-Tenant-Store-Id / X-Login-User-Id / X-Login-User-Name` 透传，ThreadLocal 用完必清。

### 1.3 契约盘点（28 个）

| provider | 契约数 | 主要实体 |
|---|---|---|
| operator | 3 | EnterpriseAccount、OperatorUser、SysDictionary |
| shop | 3 | Brand、Store、StoreManager |
| store | 15 | Dish/Category/Flavor、SetMeal/Dish、Table/Area/Log、Staff、Credit 系列、Remark、SellCalculation |
| order | 6 | Order/Detail/DetailMeal、ReverseOrder、Report*、视图 |
| es | 1 | DishEs（索引 `dish`） |

含 **2 个空占位契约**（`IDishFlavorService`、`IOrderDetailMealService`）：接口体为空、无 Controller，**不得**为其生成 HTTP 代理或端点。

### 1.4 关键状态机（浓缩）

| 对象 | 取值 | 要点 |
|---|---|---|
| 企业账号 status | 0 试用 / 1 正式 / -1 停用 | 7 天试用、到期重算、正式禁改回试用等规则**只在旧 BFF**（K9） |
| 门店 status | 1 营业 / 0 停业 | 经理侧列表恒仅营业 |
| 员工 status | 1 在职 / 0 停用 | **t_staff 新增列，Flyway V1 落地前勿联调员工登录**（K2） |
| 菜品/套餐 status | 1 起售 / 0 停售 | 停售菜品连带停售关联套餐 |
| 订单 payStatus | 0 未付 / 1 已付 | 反结账不校验原单已付（K7） |
| 订单明细 detailStatus | 1 正常/加菜 / 2 退菜 | 退菜插标记明细，原明细 -1，**只冲 totalAmount**（K10） |
| 桌台 status | 0 空闲 / 1 开台 / 2 锁定 | 反结账不回退桌台；无乐观锁（K11） |
| 沽清 remainder | 整数，无记录= -1 | 退菜回加仅限量菜，无记录会 NPE（K6） |

### 1.5 数据域（Flyway V1 输入）

operator 3 表 / shop 3 表 / store 15 表 / order 6 表 + 1 视图 / job 归档 2 表（与 order 同库）= **27 业务表 + 2 历史表 + 1 视图**；全仓无任何 `.sql`，DDL 随 V1 逆向产出。

## 二、需求分析

### 2.1 缺口分级（K1–K19 + P2）

分级口径：🔴 **阻塞上线**（不修则阶段 4/5 无法联调或数据错误）｜🟡 **影响正确性/体验**（可带缺陷上线，需排期）｜🟢 **后置/产品决策**。

| 编号 | 问题（浓缩） | 分级 | 处置阶段 |
|---|---|---|---|
| K3 | 三 web 共 19 个 `@Reference` + swagger2，pom 已无 dubbo → **编译不过** | 🔴 | 阶段 4（重写 BFF） |
| K12 | gateway 与 cash_web 同占 8085；无 routes/CORS/Sa-Token | 🔴 | 阶段 4 |
| K13 | 登录参数 password/loginPass 不统一、旧 VO 交叉错位、pageNo/pageNum 并存 | 🔴 | 阶段 4（统一映射） |
| K9 | 企业 add/update 不写状态与到期；试用/续费规则只在旧 BFF | 🔴 | 阶段 4，**建议下沉 provider** |
| K2 | t_staff 无 status 列（实体已加） | 🔴 | Flyway V1（数据层） |
| K6 | 沽清 add 无记录 NPE、只 update 不 upsert、参数名 dishNum/dishNumber 不一致 | 🔴 | 阶段 4 前 |
| K1 | `getBrandList()`、`listTableArea()` 缺方法级注解 → HTTP 不可达 | 🔴 | 阶段 4 首批 |
| K8 | 店长登录不拦停用、门店校验先于密码 | 🔴 | 阶段 4/5 |
| K16 | ES 索引无任何写入/同步代码，无数据来源 | 🔴 | 中间件阶段（方案见 3.3） |
| K17 | provider 无统一异常 advice，两层错误格式分裂 | 🟡 | 阶段 4/5 决策 |
| K7 | 反结账不校验原单已付 | 🟡 | 阶段 4/5（provider 补校验） |
| K10 | 退菜只冲 totalAmount，不回冲 payAmount/抹零/赠免 | 🟡 | 产品确认 |
| K11 | 无乐观锁，开台/换台/清台有并发竞态 | 🟡 | 必要时加 |
| K14 | 挂账流水金额字段语义可疑、还款不写 CreditLogs | 🟡 | 阶段 4 联调核对 |
| K18 | MQ 死配置（sms_exchange 未用）、catch 吞异常 | 🟡 | 后置整改 |
| K19 | job 归档物理删除、套餐头孤儿、全量单事务、System.out | 🟡 | 后置整改 |
| K15 | 常量注释错位；shopId 无 DB 唯一约束 | 🟢 | 顺手修 / V1 评估 |
| K4 | 企业「启用」无独立端点 | 🟢 | 产品决策：走编辑接口 |
| K5 | 菜品分页 N+1 | 🟢 | 后续优化 |
| P2 | 运营/字典增改、多条件筛选、区域桌台删除等 | 🟢 | 首期后置 |

### 2.2 主要风险（Top 5）

1. **业务规则丢失（K9）**：7 天试用、到期重算、正式禁改试用只在旧 Dubbo BFF。若阶段 4 只在 web 层照抄，规则会分散；**建议下沉 provider**，一处实现、五端复用。
2. **金额一致性（K10/K14）**：退菜只冲 totalAmount、挂账流水字段语义可疑，已付后退菜/还款会产生实收应收差额。需产品确认口径，再定是否红冲。
3. **索引无数据源（K16）**：ES 只读不写，中间件搭好后收银端检索仍查不到菜品。必须先定同步方案。
4. **两层错误格式分裂（K17）**：provider 裸返回 + 默认错误体，BFF 有统一信封。契约化后客户端要同时处理两种结构，联调成本高。
5. **并发竞态（K11）**：桌台状态无乐观锁，多收银端同时开台/结账会互相覆盖。教学规模可接受，但前端不得缓存桌台状态。

### 2.3 优先级与排期建议

| 阶段 | 必做（🔴） | 验收点 |
|---|---|---|
| **4 · BFF + 网关** | K3 重写三 web、K12 端口/路由/CORS、K13 参数映射、K9 规则下沉、K6 沽清、K1 补注解、K8 登录加固 | 三 web + gateway `mvn compile` 全绿；对照表 10.2 逐口联调通过 |
| **5 · 鉴权 + 中间件** | Sa-Token 全链路（B 端四套 + C 端 StpLogic）、K17 异常体系、K16 ES 同步落地、Flyway V1（含 t_staff.status） | 登录/切店/越权拦截生效；ES 检索有数据；5 库迁移成功 |
| **6 · C 端点餐** | microapp_web（8087）+ 4 页面 | 扫码点餐主流程跑通（dev 打桩支付） |
| **7 · 前端重写** | Vue3 monorepo 三端 + Taro4 点餐 | 三端构建通过、接 BFF 联调 |

> 🟡 项（K7/K10/K14/K18/K19）建议并入阶段 4/5 的联调窗口处理，不单独占阶段。

### 3.2 前端（决策重点：重写 vs 升级）

**现状（实证）**——四端全部是 2019–2020 年老栈：

| 端 | 现状 | 风险 |
|---|---|---|
| guanjia | Vue **2.6** + Element UI **2.12** + webpack **4** + TS 3.6 | Vue2 已 EOL（2023-12），依赖漏洞无人修 |
| yunyin | 同 guanjia（几乎同一套 package.json） | 同上 |
| weixin | Taro **2.1.1** + React 16 + nervjs | Taro2 老旧，升级断裂 |
| diancan | Flutter（Dart SDK `>=2.2.0 <3.0.0`、dio 2.x、bloc 0.15、fluro 1.5） | **无法在 Dart 3 / 现代 Flutter 运行**，等同事实性重写 |

**目标态（需求文档定稿）**：pnpm monorepo（apps/operator、enterprise、h5 + packages/shared），Vue **3.5** + TS + Vite **8** + Element Plus + Pinia + ECharts **6**；Taro **4.3** + React 18 + NutUI。

**建议：按定稿重写三端 + Taro 点餐，不做老栈升级。** 理由：

1. Vue2/Taro2 升级路径断裂，升级成本≈重写，且失去 monorepo 复用收益；
2. 老栈依赖（webpack4、nervjs、dio2）有安全与维护风险；
3. 需求文档已把重写列为阶段 7，BFF 契约（28 个）稳定，重写可直接对齐契约。

**Flutter 收银 APP 特别说明**：需求文档定「本轮不动」，但**当前代码无法在现代 Dart 运行**（SDK 约束 `<3.0.0`）。建议：本轮保持不动、仅记录风险；若后续要动，按「升级 Flutter 3 + Dart 3」评估，状态管理建议 Riverpod（替代老 bloc 0.15），网络层 dio 5。**不要**在旧 SDK 上继续堆功能。

### 3.3 缺口新增技术选型（建议）

| 议题 | 候选 | 建议 | 理由 |
|---|---|---|---|
| **ES 索引同步（K16）** | ①应用内双写 ②MQ 异步双写 ③Logstash/CDC | **② 菜品写后 MQ 异步双写 + 全量重建接口** | 与现有 RabbitMQ 链路复用；写库与索引解耦；重建接口兜底，配 index 别名切换 |
| **统一异常（K17）** | ①provider 引公共 advice ②BFF 层统一转换 | **① provider 统一 advice**（复用 common 的 BussinessException，对齐错误码） | 契约即接口，错误结构应随契约一致；BFF 保留信封做适配，避免两层格式分裂 |
| **鉴权（阶段 5）** | ①Sa-Token 多账号体系 ②自研 JWT 扩展 | **① Sa-Token**：B 端四套登录 + C 端独立 StpLogic | 已引入 1.46；多账号体系天然隔离 B/C 会话；切店重签含 storeId 令牌 |
| **契约测试** | ①Spring Cloud Contract ②手工 Handshake | **② 先手工 Handshake**（改共享 DTO 必通知） | 教学规模，契约仅 28 个；SCC 引入成本高，暂不需要 |
| **MQ 整改（K18）** | ①统一命名交换机 ②删死配置 | **①** 统一走命名交换机 + 死信队列；catch 改 slf4j | 与 3.3 ES 异步双写共用通道；死信防丢短信 |
| **并发（K11）** | ①@Version 乐观锁 ②状态条件更新（CAS） | **② 关键操作带状态条件 update**（如开台 where status=0） | 改动小、贴合现有「按 status 现值判断」逻辑；@Version 需全实体加列 |
| **归档（K19）** | ①维持物理删 ②补套餐头归档 + 分页批处理 | **②** 补 dishType=2 归档/删除、分页批处理、日志改 slf4j | 消除孤儿数据与单大事务风险 |
| **API 文档** | springdoc（在位） | ✅ 沿用，补 `/v3/api-docs` 白名单（K1/K15 相关） | 已依赖，阶段 4 删 swagger2 残留即可 |
| **可观测** | actuator + Prometheus + Micrometer Tracing | 按定稿，后置 | 需求文档已列，非阻塞 |
| **测试** | JUnit5 + Mockito + Testcontainers | 按定稿，核心链路优先 | Testcontainers 覆盖 MySQL/Redis/ES/RabbitMQ |

### 3.4 关键决策点（需你拍板）

1. **K9 业务规则**：确认「下沉 provider」还是「BFF 重写」？（建议下沉）
2. **K10/K14 金额口径**：已付后退菜/还款产生差额，接受还是红冲？
3. **K17 异常体系**：provider 统一 advice 还是 BFF 转换？（建议前者）
4. **前端重写范围**：确认三端重写 + Taro 点餐；Flutter APP 维持「不动」？
5. **K12 端口**：gateway 与 cash_web 冲突，gateway 换 8080 还是 cash 换？
